# W3-02 isolated attendance ingress and local kiosk

Status: local synthetic runtime verified; production and real iPOS/tunnel not run. Final parent acceptance binds the exact source and receipts.

The dedicated ingress process uses PAYSLIP_INGRESS_DATABASE_URL only, listens on 127.0.0.1:46218, and exposes GET /health, POST /clock, POST /reconcile, and three explicitly mapped kiosk assets (/, /kiosk.css, /kiosk.js). Unknown/admin/payroll/document paths return 404. Exact loopback Host and same-origin checks precede all effects; no CORS or reverse proxy. The public import graph cannot reach private admin or payroll code.

POST /clock accepts {employeeCode, pin, action: CLOCK_IN | CLOCK_OUT, idempotencyKey: UUID}. Authenticate the enrolled device through its HttpOnly cookie or Bearer token, then the employee's Argon2id PIN and active shop binding. Device-wide 20-request/minute and employee-code five-failure/15-minute limits are persisted under hashes. Device rotation/revocation serialize with clock commands. One employee-wide state row serializes transitions across devices. Append-only clock events preserve the original server UTC timestamp across authenticated idempotent retries. A changed action conflicts.

Success contains recorded:true, eventId, recordedAt, nextAllowedAction, replayed and requestId only after COMMIT acknowledgment. The requestId is also the successful audit record ID. Known failures before attempting COMMIT return recorded:false. A lost COMMIT acknowledgment returns pending_confirmation, including when the underlying database committed successfully. Never infer rollback from a lost acknowledgment.

POST /reconcile accepts employeeCode plus the original random idempotencyKey, bound to the authenticated device/session and short-lived employee proof. No PIN is required or retained. Proof lookup expires after ten minutes; an absent, wrong-code, expired or wrong-session proof remains uncertain, never a claim that a possibly committed event was not recorded. Reconciliation creates no clock event.

The kiosk uses three ordinary interactions: code, six-digit PIN, action. It clears PIN immediately, keeps only code/action/random key in sessionStorage while uncertain, and clears that state on a definitive response. Reconciliation retries at most three times automatically; unresolved outcomes remain blocked for manager assistance or explicit recheck. Shop time display uses Asia/Ho_Chi_Minh. The read-only window.paySlipKioskTools.readState capability returns outcome state and pendingConfirmation only; it cannot access or mutate payroll and exposes no PIN, code, token or request key.

Private KioskAdminRepository commands require CSRF, an active organization-bound owner session and fresh MFA, validated again in the transaction. Enrollment, rotation, revocation and PIN provisioning write admin audits. Device tokens are random and stored only as SHA-256 hashes; PINs use Argon2id. The local synthetic fixture passes enrollment through an HttpOnly browser cookie without writing raw tokens or PINs to disk. Real device enrollment delivery remains part of the future private admin/iPOS release flow.

The migration assumes the dedicated payslip_ingress role exists. It grants only device/PIN/attendance reads and attendance/proof/audit inserts, plus employee ID/org/shop/status column reads and mutable attendance/rate state updates. Direct tests deny users, names, payroll, documents, device mutation and immutable-event mutation. A fixed-search-path trigger locks the active employee during clock insertion under the migration owner. No public import of the private admin repository is permitted.

Run npm run build, then npm run test:kiosk for the owned synthetic PostgreSQL + built admin + ingress + Chromium wave. The harness creates fresh generated credentials in memory, applies migrations, runs nonempty backend/browser tests and stops exact owned processes/listeners. Temporary synthetic clusters and receipts are retained. Run npm run test:auth:browser separately for the guarded auth database. npm run test:e2e invokes real Playwright and requires the appropriate prestarted fixture/environment; it does not silently invent database authority.
